# 桌面 Lighthouse `/apps/` CLS 0.047（PR #4 push run 40630747358）——根因与修复

日期：2026-10-28（CST）。分支 `fix/batch1-admin-read-settings-guard`（PR #4），失败头 `2065934`。
门槛：桌面 CLS ≤ 0.02（站长 2026-10-27 定稿，硬门槛；不允许靠重跑或推迟采样过关）。

## 结论

- **真实的布局问题，不是测量噪声，也不是本轮改动引入的。** `/apps/` 的 HTML 约 124 KB，Chromium 在解析到列表之前会先画一帧
  （首帧时主栏只解析出「更多筛选」，列表 0 个条目）。≥ 1200 时主栏 `.list-main` 和左侧分类栏在同一网格行，被拉到分类栏高度
  （258px）；`.list-main:has(> .filter-bar)` 是网格，`align-content` 默认 `normal`（= stretch）把唯一的 auto 行一起拉高，
  行内 `align-items: center` → 首帧「更多筛选」在 y = 340，条目到齐后回到 y = 255，**跳 85px**。
- 这正是 PR #6 `c48bada`（2026-10-27）已经修过的那个问题；但修复只在 #6（及候选 #7 `56b6a70`）里，
  #4 / #5 基于的 `v2/astro` 仍是旧样式（规则来自 `8f433c9`）。`main` 没有这条规则（旧版页面），不受影响。
- 本轮 `2065934` 与 `cdee2ca` 的 `/apps/` 产物逐字节比较：HTML 去掉文件名哈希后完全一致、内联 CSS 一致，页面引用的 3 个脚本
  只差内部 chunk 文件名（大小相同）。所以 0.047 不是 fail-closed 改动造成的，是这个首帧时序偶发命中。

## 修复（PR #4，只改 CSS）

`src/styles/store.css`：`.list-main:has(> .filter-bar) { align-content: start; }`（行高只由内容决定，多余高度留在网格底部）。
文字与 PR #6 `c48bada` 的同一处**逐字相同**，之后 #6 合并时这一段是相同改动，不会冲突。

`c48bada` 里另外两处（「更多筛选」与工具条统一上下外边距、工具条里分段控件 24px 下外边距归零）**没有搬过来**：它们会改最终布局
（列表上移约 20px），#4 的 `/apps/`、`/ai/` 等视觉基线要重做；PR #6 已带这两处并已重审基线。只差的那一段：
工具条还没解析的那一帧「更多筛选」会比最终位置高 22px（158×44 的按钮，CLS 约 0.0001）。

最终布局不变：本机修复前后 `/apps/`（1024 / 1350 / 1440 / 1920 / 2560 / 390）、`/ai/`（1024 / 1440）、`/apps/category/creative/`、`/en/apps/`
整页截图逐像素比较，差异像素全部为 0。没有改任何脚本，`/apps/` JS 预算（49,152 B）不受影响。
